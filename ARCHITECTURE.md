# Архитектура Ventilyator

Модульный монолит NestJS и отдельный BullMQ worker, единая PostgreSQL и единый API. Caddy принимает браузерные запросы, `/api/*` направляет в API, остальные — в web-контейнер React. Клиент не получает секреты и прямой доступ к БД/дискам. Крупный редактор документов загружается отдельным маршрутом.

## Ответственность компонентов

- PostgreSQL: пользователи, роли, проекты, задачи, знания, версии, файлы/квоты, настройки, уведомления и outbox.
- Redis: серверные сессии, ограничения входа, BullMQ и heartbeat. Политика noeviction исключает произвольное вытеснение очередей/сессий.
- Storage на Ubuntu: версии файлов и ключ шифрования SMTP. API выдаёт только защищённые маршруты скачивания.
- API: Identity, Projects/Tasks/Planning, Knowledge, Files, Portal, административные Users/Roles/Mail.
- Worker: BullMQ health jobs, outbox email и дедуплицированные напоминания о сроках.
- Web: рабочий стол, проекты/планирование, знания/редактор, поиск/уведомления/календарь и администрирование.

## Изоляция и запись

Организация/пользователь берутся из серверной сессии. Проектные права задаются владельцем/участием и projects:manage; знания — участием/knowledge:manage. Личный черновик отделён от общей публикации, неопубликованная страница закрыта от обычных читателей. Файл наследует контекст задачи или страницы. Поиск, отчёты и email повторно учитывают ACL. Составные FK дополняют проверки сервиса.

Номера задач и изменение проекта сериализуются блокировкой проекта; документы — пространства. Optimistic version/revision не допускает тихой перезаписи. Зависимости проверяются на циклы, завершение задачи — на блокирующие зависимости. Workflow и WIP проверяются сервером по всей БД, а не по видимой странице доски. Номер активного спринта дополнительно защищён partial unique index.

БД и файловая система не являются одной транзакцией: билеты/lease/журнал StorageUpload и администраторская сверка позволяют завершать/убирать незавершённые операции. SHA-256, безопасные имена, резервирование диска и необязательный ClamAV предшествуют публикации метаданных.

## Фоновая работа

Событие и уведомление создаются в одной транзакции. EmailDelivery — постоянный outbox; worker переносит его в BullMQ, проверяет права, настройки и активность перед SMTP. Job/message ID стабильны, попытки/lease ограничены; редкая повторная доставка после аварии SMTP возможна. Очередь восстанавливается из PostgreSQL после очистки Redis. Напоминания имеют уникальный eventKey с задачей/сроком/фазой.

## Развёртывание

API/worker стартуют после успешной миграции. Readiness проверяет PostgreSQL, Redis, storage и heartbeat worker; liveness проверяет HTTP-процесс. Секретная конфигурация в публичные ответы не включается. Приложения работают UID 1000, read-only root, tmpfs и без capabilities. PostgreSQL/Redis не публикуют порты; backend-сеть internal. API и worker дополнительно имеют frontend-сеть для настроенной почты.

Email глобально уникален, одна учётная запись принадлежит одной организации. Для нескольких организаций нужен отдельный Membership. WebSocket/CRDT/автоматизация/согласования не реализованы; обновления интерфейса сейчас опрашиваются. Точный остаток — ROADMAP.md.
