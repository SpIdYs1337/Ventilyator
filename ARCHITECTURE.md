# Архитектура Ventilyator

Модульный монолит NestJS и отдельный BullMQ worker, единая PostgreSQL и единый API. Браузер обращается к Caddy, который маршрутизирует `/api/*` в backend, остальные запросы — в отдельный web-контейнер. React не получает секреты и прямой доступ к базе или дискам.

## Границы

- PostgreSQL — постоянные структурированные данные, идентичности, роли, аудит, метаданные сессий и файлов.
- Redis — содержимое серверных сессий, ограничения попыток входа, heartbeat, очередь. Политика `noeviction` исключает вытеснение активных сессий из-за переполнения; вместо этого требуется вмешательство администратора.
- Worker — только явно поддерживаемые виды заданий. Сейчас реализован проверочный `health-probe`, выполняющий реальный SQL-запрос. SMTP будет отдельным обработчиком следующего этапа.
- Storage — только серверная локальная файловая система. Корневой каталог и служебные каталоги проверяются на символические ссылки при запуске. Файловый API ещё не реализован.

## Организации и доступ

`User`, `Role`, `AuditEvent`, `StorageObject` и `Project` принадлежат организации. API использует организацию из проверенной серверной сессии; организация из входного JSON не принимается. Роли дают разрешения на функции. Модуль `apps/api/src/work` проверяет доступ к проекту через владельца/участие либо явное разрешение `projects:manage` в своей организации; административные разрешения пользователей/системы этого не заменяют. Задачи, комментарии и история наследуют ACL проекта. Составные FK защищают организационные границы. ACL документов предстоит реализовать вместе с базой знаний.

Email пока глобально уникален: одна локальная идентичность принадлежит одной организации. Для одного человека в нескольких организациях потребуется отдельная модель Membership; это отмечено в дорожной карте.

## Устойчивость

Выполняется отдельный одноразовый контейнер миграций; API и worker стартуют после его успеха. Liveness отражает работу HTTP-процесса, readiness проверяет реальное подключение к PostgreSQL/Redis, запись в storage и свежий heartbeat worker. Публичная проверка не раскрывает конфигурацию. Подробности доступны только с `system:read`.

Все контейнеры приложений работают как UID 1000 без capabilities и с read-only root filesystem; временные файлы пишутся в tmpfs. Backend и frontend разделены сетями; PostgreSQL/Redis наружу не публикуются. Backend-сеть internal. IMAP требует исходящего подключения из API через frontend-сеть; worker пока не имеет исходящего SMTP-доступа — его следует добавить явно при реализации почтовой очереди.

## Последовательность

Полная спецификация сохранена в `docs/requirements.md`. Локальные пользователи и их создание через веб-панель обязательны. IMAP и уведомления обязательны к реализации, но включаются независимо и не являются prerequisites для основной работы. Детальный порядок — в ROADMAP.md.
