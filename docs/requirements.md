# MASTER PROMPT: VENTILYATOR

## Полная разработка корпоративной платформы управления задачами, проектами и знаниями

# 1. Роль разработчика

Ты — ведущий Software Architect, Senior Fullstack Developer, DevOps Engineer, Database Architect, UI/UX Designer и специалист по информационной безопасности.

Твоя задача — с нуля спроектировать, разработать, протестировать и подготовить к эксплуатации полноценную корпоративную информационную платформу под названием **Ventilyator**.

Это должен быть не прототип, не MVP с ограниченным функционалом и не демонстрационный макет, а самостоятельный программный продукт, пригодный для реального ежедневного использования сотрудниками организации.

Разрабатывай Ventilyator как единую модульную систему, а не как набор разрозненных приложений.

Все основные функции должны работать с реальной базой данных, полноценным backend и действующими механизмами безопасности.

## 1.1. Главная цель

Ventilyator — единая корпоративная платформа для:

- Управления проектами.
- Постановки и выполнения задач.
- Управления рабочими процессами.
- Ведения корпоративной базы знаний.
- Совместного редактирования документации.
- Хранения внутренних файлов и вложений.
- Планирования деятельности подразделений.
- Работы с командами и сотрудниками.
- Учёта рабочего времени.
- Согласования внутренних запросов.
- Контроля сроков.
- Автоматизации операций.
- Формирования аналитики и отчётности.
- Управления уведомлениями.
- Централизованного администрирования.

Название во всех интерфейсах, исходном коде, документации, API и Docker-конфигурациях: **Ventilyator**.

Используй полностью оригинальный интерфейс, графику и фирменный стиль.

Основной язык системы — русский. Архитектура должна поддерживать добавление других языков, первоначально английского.

# 2. Условия эксплуатации

Ventilyator будет установлен на виртуальной машине Ubuntu Server LTS во внутренней сети организации.

Система предназначена для постоянной работы на собственном сервере.

## 2.1. Обязательные условия

- Полностью самостоятельная установка.
- Развёртывание через Docker Compose.
- Работа внутри локальной сети.
- Отсутствие обязательных облачных сервисов.
- Отсутствие внешних SaaS-зависимостей.
- Отсутствие лицензирования по числу пользователей.
- Отсутствие обязательной регистрации во внешних системах.
- Хранение всех данных на локальных дисках Ubuntu.
- PostgreSQL в локальном Docker-контейнере.
- Redis в локальном Docker-контейнере.
- Собственный backend.
- Собственный frontend.
- Собственная система файлового хранения.
- Возможность работы без интернета после установки.
- Автоматический запуск после перезагрузки Ubuntu.
- Сохранение данных после перезапуска и обновления контейнеров.
- Поддержка резервного копирования.
- Возможность обновления без потери данных.
- Поддержка внутренних DNS-имён.
- Поддержка корпоративных TLS-сертификатов.

Допускается взаимодействие с настроенными администратором IMAP/SMTP-серверами. Оно не должно создавать зависимости от внешнего облака для основных функций Ventilyator.

## 2.2. Доступ

Пользователи работают через браузер:

```text
https://ventilyator.company.local
```

Адрес является примером и должен задаваться через конфигурацию.

Обеспечь доступ с Windows, Linux, macOS и мобильных браузеров.

Система должна корректно работать без установки клиентского программного обеспечения.

# 6. Пользователи и авторизация

Создай полноценную систему Identity & Access Management.

## 6.1. Способы входа

Реализуй:

1. Локальную авторизацию.
2. Авторизацию через IMAP.
3. Возможность расширения на LDAP / Active Directory.

Локальные пароли хешируй с Argon2id.

Никаких паролей в открытом виде в базе данных.

## 6.2. IMAP-авторизация

Администратор должен иметь возможность настроить авторизацию сотрудников через корпоративную электронную почту.

Настройки:

- IMAP host.
- IMAP port.
- TLS mode.
- Connection timeout.
- Allowed domains.
- Auto-create users.
- Default role.
- Login mapping.
- Test connection.
- Enable / Disable IMAP authentication.

Пользователь открывает Ventilyator, вводит email и пароль.

Backend проверяет учётные данные через заранее настроенный IMAP-сервер.

При успешной проверке создаётся локальная учётная запись либо находится уже существующая, после чего создаётся локальная сессия Ventilyator.

Пароль от электронной почты не должен сохраняться ни в PostgreSQL, ни в Redis, ни в логах приложения.

Нельзя допускать подмену IMAP-хоста пользователем.

Соединение должно быть защищено TLS с проверкой сертификата.

Запрети небезопасное понижение уровня защиты соединения.

Предусмотри работу с почтовыми серверами, требующими пароль приложения или OAuth2, через расширяемый интерфейс провайдера авторизации.

Учти, что IMAP-авторизация возможна только там, где почтовый сервер поддерживает соответствующий механизм проверки учётных данных.

Связывание существующей локальной учётной записи с IMAP-идентичностью должно выполняться по проверенным правилам, исключающим захват чужой учётной записи.

## 6.3. Сессии

Сессии должны быть достаточно продолжительными, чтобы сотрудники не проходили авторизацию несколько раз в день.

Реализуй:

- Серверные сессии в Redis.
- HttpOnly cookies.
- Secure cookies при HTTPS.
- SameSite.
- Защиту от CSRF.
- Sliding expiration.
- Продление активной сессии.
- Возможность «Запомнить меня».
- Просмотр активных сессий.
- Выход с отдельного устройства.
- Выход со всех устройств.
- Отзыв сессии администратором.
- Журнал авторизаций.
- Ограничение количества сессий по настройке.

Значения по умолчанию:

| Параметр | Значение |
|---|---|
| Обычная сессия | 7 дней при активности |
| Запомнить меня | До 30 дней |
| Несколько устройств | Разрешено |
| Продление активной сессии | Включено |
| Максимальное время жизни | Настраивается |
| Принудительный выход | Поддерживается |

Применяй абсолютный предел жизни сессии с возможностью безопасного продления после повторной аутентификации.

Не допускай потери несохранённого текста при завершении сессии: реализуй восстановление пользовательских черновиков.

Не используй localStorage для хранения сессионных секретов.

## 6.4. Роли

Стандартные роли:

- System Administrator.
- Organization Administrator.
- Department Manager.
- Project Administrator.
- Team Member.
- Viewer.
- Guest.

Реализуй собственные роли, собственные наборы разрешений и объектные ACL.

# 12. Собственная система хранения файлов

## VENTILYATOR LOCAL STORAGE

Это обязательный архитектурный компонент.

**Никакого S3, MinIO, AWS, облачных файловых сервисов и S3-совместимых интерфейсов.**

Все файлы должны храниться в локальной файловой системе Ubuntu Server.

При этом хранение должно быть систематизированным, отказоустойчивым и управляемым.

## 12.1. Общий принцип

Используй два независимых уровня.

### Физический уровень

Хранит непосредственно байты файлов на локальных дисках Ubuntu.

### Логический уровень

Хранит в PostgreSQL:

- Названия.
- Владельцев.
- Категории.
- Папки.
- Проекты.
- Связанные задачи.
- Связанные документы.
- Размеры.
- MIME-типы.
- Контрольные суммы.
- Версии.
- Права.
- Время создания.
- Время изменения.
- Историю операций.

Пользователь работает с логическими папками и объектами, а не с физическими путями.

## 12.2. Физическое расположение

Основной каталог:

```text
/srv/ventilyator/
```

Структура:

```text
/srv/ventilyator/
│
├── storage/
│   ├── objects/
│   │   ├── ab/
│   │   │   └── cd/
│   │   │       └── <object-uuid>/
│   │   │           ├── v0001.bin
│   │   │           ├── v0002.bin
│   │   │           └── v0003.bin
│   │
│   ├── previews/
│   ├── thumbnails/
│   ├── temporary/
│   └── quarantine/
│
├── postgres/
├── redis/
├── backups/
├── config/
└── logs/
```

Структура является рекомендуемой и может уточняться.

Файлы распределяются по каталогам с использованием UUID и префиксов идентификаторов.

Запрещено формировать физический путь из пользовательского имени файла.

Переименование задачи или документа не должно перемещать физический файл.

## 12.3. Логическая структура

Пользователь видит:

```text
Организация
│
├── Общие файлы
│   ├── Регламенты
│   ├── Шаблоны
│   └── Прочее
│
├── Проекты
│   └── Проект A
│       ├── Документы
│       ├── Вложения задач
│       └── Материалы
│
├── База знаний
│   └── Пространство A
│       └── Файлы страниц
│
└── Личные файлы
```

Логические папки могут быть вложенными.

Один физический объект может быть связан с несколькими разрешёнными объектами системы без обязательного дублирования его байтов.

Разрешения при этом определяются для конкретной связи и контекста доступа.

## 12.6. Загрузка

Загрузка файлов должна работать потоковым способом.

Алгоритм:

1. Проверка авторизации.
2. Проверка разрешений.
3. Проверка квоты.
4. Создание временного файла.
5. Потоковая загрузка с ограничением размера.
6. Проверка фактического формата и контрольной суммы.
7. Антивирусная проверка, если включена.
8. Атомарное перемещение в постоянное хранилище.
9. Создание метаданных.
10. Подтверждение успешной операции.

Предусмотри согласование состояния файловой системы и PostgreSQL: запись файла и запись в БД не являются одной транзакцией.

Для защиты от сбоев используй состояния операций, идемпотентность и механизм восстановления незавершённых загрузок.

## 12.7. Безопасность файлов

Обязательно:

- Защита от path traversal.
- Проверка владельца и разрешений.
- Защита от symlink-атак.
- Безопасное разрешение путей.
- Ограничение размера загрузок.
- Проверка фактических типов файлов.
- Запрет исполнения файлов.
- Безопасная выдача Content-Disposition.
- Защита от XSS через вложения.
- Защита от несанкционированного скачивания.
- Защита от обхода ACL через прямую ссылку.
- Запрет прямого доступа к каталогу через reverse proxy.

Добавь локальную интеграцию с ClamAV как дополнительный включаемый компонент. При включённой обязательной антивирусной проверке недоступность сканера должна блокировать публикацию новых файлов.

## 12.8. Диски

Предусмотри возможность:

- Использовать отдельный виртуальный диск.
- Увеличивать размер файлового раздела.

## 12.9. Docker

Подключай хранилище через bind mount:

```yaml
volumes:
  - /srv/ventilyator/storage:/app/storage
```

Этот каталог должен подключаться только к backend-процессам, которым требуется непосредственный файловый доступ.

Frontend не должен иметь доступ к filesystem.

Файлы должны выдаваться пользователям только через авторизованный API.

## ГЛАВНОЕ ТРЕБОВАНИЕ

**Ventilyator должен стать полностью автономной корпоративной платформой, которая объединяет управление задачами, проектами, знаниями, документами, файлами, уведомлениями и рабочими процессами в одном интерфейсе.**

Все данные, включая PostgreSQL и физические файлы, должны находиться под полным контролем организации на собственном Ubuntu Server.

Никаких обязательных облачных компонентов.

Никаких S3-интеграций.

Никаких демонстрационных подмен функциональности.

Приоритеты: сохранность данных, безопасность, удобство пользователей, стабильность, поддерживаемость и полнота реализации.

**Начни разработку проекта Ventilyator с этапа 1 прямо сейчас.**
